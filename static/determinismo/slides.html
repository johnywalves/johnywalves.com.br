O pipeline generativo

1
Prompt
O texto que entra.
"O cliente pode cancelar? Resposta:"
2
Tokens
O texto é cortado em pedaços e cada pedaço vira um número.
O · cliente · pode · cancelar → 46 · 23508 · 9684 · 169134 …
3
Embeddings
Cada número vira um vetor que representa significado.
169134 → [0,12  −0,87  0,33 …]
4
Atenção
Cada token pesa quais outros importam para o contexto.
"cancelar" olha para "cliente" e "pode"
5
Distribuição
O modelo calcula a probabilidade de cada próximo token.
sim 42% · não 23% · talvez 15% · …
6
Amostragem
Um token é sorteado dessa distribuição.
sorteou "sim"
7
Texto
O token entra no contexto e o ciclo repete até terminar.
"sim" volta ao passo 2

Aqui nasce a variabilidade: passos 5 e 6.

IDs do passo 2 são reais (tokenizador o200k_base). Vetor, atenção e probabilidades são ilustrativos; as reais aparecem no slide 8.

Três fontes, não uma

1

Hardware / GPU

Não-associatividade de ponto flutuante + batching dinâmico.

2

Interpretação

Deriva de interpretação da tarefa. A mais subestimada.

3

Saída

Espaço de saída livre: formato e semântica variam.

Fonte 1: GPU e batching

A ordem de acumulação depende do batch.
O batch varia em produção.
A saída varia.

Mesma entrada, mesmo modelo, mesmo temperature=0.
Execuções diferentes, saídas diferentes.

Fonte 2: deriva de interpretação

Interpretação A

Coerente internamente. Mas incompatível com B e C.

Interpretação B

Coerente internamente. Mas incompatível com A e C.

Interpretação C

Coerente internamente. Mas incompatível com A e B.

Engenharia de prompt ajusta a probabilidade de escolha dentro do espaço de interpretação.
Não elimina a diversidade de interpretações.

Fonte 3: espaço de saída livre

JSON

{"acao": "cancelar", "motivo": "..."}

Prosa

"Claro, posso ajudar com o cancelamento..."

Lista

1. Cancelar
2. Reembolsar
3. Confirmar

Mesmo com temperature=0, texto livre permite variação de formato e desvio semântico.

Como chegar ao determinismo funcional?

Com um portão determinístico na arquitetura: o System One.

1 System One decide 2 Especificação fecha o sentido 3 System Two executa

São três camadas. Hoje começamos pela primeira.

O que é System One

Definição

System One aqui não é o "pensamento rápido" cognitivo de Kahneman. É um sistema de execução de decisão local e não generativo, implantado na camada de arquitetura. Toma decisões determinísticas por meio de limites de regras predefinidas, classificadores de intenção e mecanismos de auditoria, um "portão de controle" antes do LLM.

Nos dados deste deck, o System One é o Jev 1.13: recebe uma mensagem e perguntas, e responde só dentro de opções fechadas.

Função 1: espaço aberto vira espaço fechado

"quero cancelar minha assinatura e pedir reembolso"
System One
["billing", "tech_support", "security"]

"Smart if-statements": classificação em enumeração predefinida. Mesma entrada + mesmo modelo + parâmetros fixos = mesma decisão.

Função 2: auditoria (ActionLedger)

Decisão
Registro no ledger
Verificação
Execução
  • Reconstruibilidade: rastrear decisão até política e entrada.
  • Invariância de ordem: a decisão não muda quando a ordem das opções muda.
Ilustrativo [billing, tech, security] → billing Ilustrativo [security, billing, tech] → billing

LLMs tendem a favorecer a primeira ou a última opção da lista. Se embaralhar a lista muda a decisão, a decisão depende da posição, não do conteúdo.

O que o System One troca

Ganha

Confiabilidade · auditabilidade · determinismo funcional.

Perde

Flexibilidade com o inesperado, latência extra e manutenção da taxonomia. Entradas fora da enumeração precisam de fallback.

~0,35 s mediana do portão (112 chamadas) 2,9 a 4,2 s mediana de uma chamada ao LLM
System One não gera.
Ele decide, registra e limita.

Requisição realrun.mjs · mesma especificação para os 4 modelos

Especificação: o que os modelos recebem

1 · Política (prompt de sistema)

Você é o módulo de classificação de um chat de suporte. Siga a política billing.cancellation.v3.
- "cancelar" = encerrar a assinatura ao fim do ciclo atual.
- "reembolso do mês passado" = reembolsar o ciclo de cobrança anterior.
- Intenções permitidas: billing_agent, tech_support, security_review.
- Ações permitidas: cancel_subscription, refund_previous_cycle, em ordem alfabética.
Responda somente com o JSON do schema. Nunca escreva texto fora do JSON.

2 · Requisição e schema estrito

{
  "messages": [
    { "role": "system",
      "content": /* política ao lado */ },
    { "role": "user",
      "content": "quero cancelar e pedir reembolso do mês passado" } ],
  "response_format": { "type": "json_schema",
    "strict": true, "schema": {
      "intent": enum [billing_agent,
        tech_support, security_review],
      "actions": [enum cancel_subscription,
        refund_previous_cycle],
      "refund_cycle": enum ["previous"],
      "additionalProperties": false } },
  "temperature": 0 // GPT 6.1 Sol recusa 0 (só aceita 1)
}

Política fecha o sentido. Schema fecha a forma. Sem isso, o controle recebia só: "Responda ao cliente."

O que o System One não resolve

Não resolve

  • Raciocínio complexo (papel do System Two)
  • Entradas fora da enumeração (fallback)
  • Manutenção da taxonomia ao longo do tempo

Riscos

  • Viés embutido nas regras de classificação
  • Falsa sensação de segurança
  • Determinismo não é sinônimo de justiça

Para levar

  • Determinismo não é binário. Escolha o nível certo para a tarefa.
  • Temperature=0 não garante reprodutibilidade. GPU, batching e interpretação importam.
  • System One transforma entrada aberta em decisão fechada.
  • Especificação determinística faz até modelos diferentes convergirem byte a byte.
  • Controle vem da arquitetura em camadas. E toda rigidez tem custo.
